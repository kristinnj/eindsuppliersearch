# M1 structural gate and migration (P0-03B.1)

Source version **1.2.0** adds storage only. No existing installation has been
upgraded by this work. Keep supplier commerce disabled. Review the root report
`docs/development/evidence-storage-m1-p0-03b1.md` before operational use.

Run the independent gate explicitly:

```sh
EIND_M1_VERIFY_CONFIG=/private/m1-reader.json php bin/verify-evidence-m1.php --mode=structure --phase=M1 --json
```

JSON is always written to stdout. Without `--json`, a brief human summary is also
written to stderr. Exit 0 means valid M1 structure only; 1 means established
integrity failure; 2 means incomplete operational verification (takes precedence).
Reports retain known findings, identify manifest hashes, attempted object counts,
checks and unassessed domains, and always set `commerce_eligible=false`.
Authentication, contents, quotes, creation history, native products, cart,
checkout, attribution, history validity and deployment authorization are unassessed.
No signing keys or native application bootstrap are used.

Supply a private JSON file outside version control with these fields (replace
placeholders; this example is not a runnable configuration):

```json
{"host":"DB_HOST","port":3306,"database":"DB_NAME","prefix":"ps_","user":"M1_READER","password":"PRIVATE_PASSWORD","server_hostname":"EXPECTED_SERVER_HOSTNAME","metadata_definer":"METADATA_ACCOUNT@HOST"}
```

The target must match literal installed `app/config/parameters.php` host, port,
database and prefix, plus queried DATABASE()/@@hostname. Ambiguous or unreadable
configuration fails before a database connection is opened. The supported installed
PHP syntax is exactly `<?php return ['parameters' => [...]];`, with `array(...)`
also accepted. Arrays have unique identifier-shaped string keys; values may be
nested literal arrays, single-quoted PHP strings, unsigned decimal integers, or
`true`/`false`/`null`. Comments are ignored as trivia. Duplicate keys (even equal
values), double-quoted strings, expressions, variables, includes, additional root
keys/statements, closing PHP tags and other structures are unsupported and rejected;
the file is never executed. Host, database name, prefix and port keys must all be
present. Host/name/prefix must exactly match; an explicit null or empty port means
3306, otherwise a valid integer or canonical decimal string must match the configured
port. Nonstandard legitimate configurations fail closed and require separate review.

Prefix is ASCII letters/digits/underscore, possibly empty.
The operational maximum is **32 bytes** because the required existing capability
view suffix is 32 bytes; the two-table schema helper independently supports up to
41 bytes, respecting the nine-table contract's longest future suffix. Unsupported
identifiers reject before DDL; names are never truncated.

The reader requires exactly database-wide SELECT and SHOW VIEW (optional USAGE),
no other privileges, roles or grant option. Existing administrator-managed
`<prefix>eind_upgrade_trigger_metadata` and
`<prefix>eind_upgrade_metadata_capability` definer views must satisfy the existing
metadata visibility contract. Their definition and definer global TRIGGER
capability are checked independently. The gate never provisions views or grants;
hidden metadata is an operational failure. See the existing verifier README for
that separately provisioned metadata prerequisite. This gate remains separate
from the unchanged module-upgrade verifier and bounded recovery command.

## Migration prerequisites and behavior

Fresh install and `upgrade/upgrade-1.2.0.php` call `installEvidenceM1Schema()`.
This requires **EIND_M1_MIGRATION_CONFIG**, a private JSON file with the same
fields and separately approved migration credentials. It never falls back to the
broad PrestaShop account. This account needs the same SELECT/SHOW VIEW policy plus
CREATE restricted to the two fully qualified M1 table names. No evidence INSERT,
UPDATE, DELETE, native DML or automatic GRANT is required. The reader command
rejects this writer account. Plan metadata provisioning and deployment approval
separately; none is performed here in existing environments.

Migration verifies target, grants, enforcement and canonical registry; takes a
separate database/prefix advisory schema lock; validates every retained M1 object
before any CREATE; creates only absent tables; then independently checks metadata.
SQL resources are hash-checked against the frozen contract. No IF NOT EXISTS,
ALTER, DROP, destructive repair, evidence rows or registry writes occur. Session
strictness is scoped to the dedicated migration connection and restored.
All deployment actors must honor the schema lock and deployment quiescence;
the lock is not a native-operation fence.

MariaDB DDL is not assumed reversible. A failure can leave one or both tables.
Retain them and diagnose with the read-only gate. A retry verifies retained
objects and creates only missing objects; incompatible or unexpected objects
block. Unknown DDL results require independent verification, not cleanup.
Uninstall and application rollback retain M1 and ownership evidence. Do not run
reinstall/reset as recovery. Later phase or unexpected module namespace objects
fail this full M1 manifest. Every index column must expose ascending (`A`)
`information_schema.STATISTICS.COLLATION`; descending, missing or unknown directions
fail. CHECK comparison tokenizes the supported frozen subset, preserves literal
bytes and grouping, removes identifier backticks and folds unquoted token case.
Only the known MariaDB BINARY CAST/REGEXP rewrites are equated. Backslashes, doubled
quotes, comments, malformed grouping and unsupported tokens are rejected with
`M1_CHECK_UNSUPPORTED`; no SQL escape mode is guessed.

Existing bounded recovery is deliberately pinned to source 1.1.0 and refuses
1.2.0. It does not recover M1; its eligibility and semantics are unchanged.
Existing module-upgrade verification attests its original registry scope only.
Native lifecycle fixtures remain pinned to their historical 1.1.0 baseline.
Neither tool's success substitutes for the new M1 gate.

## Disposable tests

```sh
php vendor-dev/bin/phpunit -c phpunit.xml.dist --do-not-cache-result
python3 tests/M1Database/run-disposable.py --disposable
```

The M1 runner creates a new isolated internal network, database container and
owned volume, verifies ownership labels/topology and SQL identity before fixture
mutation, composes the existing database guard with a private ownership manifest,
and removes only resources it owns. No published database ports or existing
volumes are used. Accounts and unsigned synthetic rows exist only there.
The separate suite uses `phpunit.m1.xml.dist`; ordinary unit discovery excludes it.
Do not aim it at an existing database.

Structural metadata cannot establish HMAC validity, canonical JSON, supplier
provenance or logical dependencies. MariaDB permits binary padding, ASCII trailing
space equivalence, decimal rounding and nullable CHECK UNKNOWN; future approved
application validators must address these before persistence. Current connection
settings cannot prove historic writers enforced constraints.
